# 维护者指南

## 发布到公司 Git

仓库根目录必须包含 `.codebuddy-plugin/marketplace.json`，不能再套一层目录。当前维护者指定 https://github.com/LYH4Real/FIBOO-Digital-Workforce 并明确选择暂时公开发布。员工可直接读取，只有维护者发布新版本。未来需要只限公司读取时，可改为私有并为员工配置 Git 权限。

给员工分发 release.py 生成的 ZIP。可在仓库根目录增加 `distribution.json`，格式为一个包含真实 `source` 字段的 JSON；安装入口会读取该字段。`source` 是无凭据的公司 Git 地址，不要内嵌 Token。尚无真实地址时不填示例域名，员工安装器会明确询问。

首次正式发布前，检查：所有六插件验证通过、目标仓库可见性符合维护者选择、员工可完成安装和各服务独立授权。Git 传输认证沿用公司现有方式；本包不创建或托管员工账号。本机隔离配置验证不能当成第二台真实电脑的授权验收。

## 更新已有插件

1. 在 `plugins/<名称>` 修改实现或替换已验证运行时。
2. 如修改了 Wave 或采集 MCP，使用各自 `scripts/build.ps1` 重建，并更新许可证和运行时 SHA256 清单；执行其离线自检。单独改源码不等于已经更新所分发的 exe。
3. 递增插件版本并写更新说明：

```powershell
python scripts/release.py bump xiaohongshu-content-planner --part patch --note "修正参考图参数校验"
python scripts/release.py validate
python -m unittest discover -s tests -v
python scripts/release.py build --output dist/fiboo-marketplace-1.0.1.zip
```

4. 检查 Git diff，提交变更和 `release-lock.json`，推送公司发布分支。建议为发布创建有注释的 Git tag，便于审计。
5. 用试点员工执行 check-updates，确认版本差异可见；执行原生 `sync`，在新任务中核实运行版本。无人干预的原生升级需要另外验收，不能用开关已开启代替。

`plugin.json` 是每个插件版本的唯一来源。市场条目不重复写插件版本。市场总体 `version` 可按一次发布递增，但只递增市场版本不能替代插件版本变化。

`release-lock.json` 记录已打包插件版本与文件摘要。插件内容有变而版本未变时校验失败，防止客户端按旧版本缓存继续使用。不要为了通过校验删除锁文件；修改后正常升版本。

## 上新插件

```powershell
python scripts/release.py new fiboo-weekly-report --description "FIBOO 周报汇总"
```

随后实现新插件的技能、脚本或 MCP，写完整 README，声明其他插件依赖并做真实验证。新建命令只生成开发骨架，不能替代业务实现。

清单位置：`plugins/<名称>/.codebuddy-plugin/plugin.json`。Skill 放在 `skills/<skill>/SKILL.md`；MCP 使用 `${CODEBUDDY_PLUGIN_ROOT}` 引用包内文件，用户数据保存到插件缓存外。不要写维护者机器绝对路径。

同市场依赖使用字符串，例如 `"dependencies": ["dingtalk-cli"]`，原生安装器会安装依赖。若以后改用版本范围，要同时采用客户端要求的插件 Git 标签发布约定并验证解析，不能只增加一个版本字符串。

## 自动更新与回退

员工安装入口通过 WorkBuddy 原生 API 设置本市场 `autoUpdate=true`，并安装 Windows 每日/登录时只读检测。检测任务只比较版本并报告，安装和升级始终由 WorkBuddy 原生接口处理，不与宿主争写插件缓存。检查 status 时应同时看开关、上次更新时间与实际已安装版本；更新报告还包含最近一次检测和离线状态。

发布新插件不会强制安装到所有人。原生同步更新已安装插件及其依赖，定时检测任务本身不升级。升级后应在新任务中核实插件版本，必要时重启 WorkBuddy；进行中的任务可能继续使用旧版本。

出现问题时优先用“新版本号发布旧的已验证内容”回退。例如有问题的 0.3.3 发布后，把 0.3.2 的实现恢复并发布 0.3.4；保留说明及 Git 历史。这样仍遵守版本缓存机制，不手改员工 registry 或缓存。重新执行离线验证再发布。

## 六项资产的维护边界

- **Kimi**：公司市场管理技能和安装器；浏览器商店管理扩展。`runtime.json` 固定官方程序 URL 与哈希，升级时保持技能/程序匹配，验证浏览器连接。
- **钉钉 CLI**：更新 `bin/dws.exe`、配套技能及来源记录，保留 Apache-2.0 许可证。账号配置永不打包。
- **Wave / 小红书采集**：源码、Windows 运行时和依赖许可证随包；重建后校验 MCP initialize/tools/list 及错误处理，付费生图属于另行明确的业务测试。
- **fiboo 产品资料**：实时业务数据不写入技能，维护查询逻辑与资料源配置。
- **内容策划**：维护流程、输出检查和与当前 MCP 的参数合同，回归测试使用合成材料。
