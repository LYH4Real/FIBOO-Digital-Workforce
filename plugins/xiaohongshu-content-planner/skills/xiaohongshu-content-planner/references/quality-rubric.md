# 质量评测标准

仅拆解时检查素材真实性、分析完整性与范围匹配；不以缺少目标产品或未生图判定失败。默认生产完成文件、格式、数量和实际尺寸检查后即交付图片，内容由用户人工审稿，状态为“待人工审核”。不默认启动独立 Agent/视觉工具、制作审查裁剪/放大图、七项评分或视觉自动重试。

以下成品硬门槛和100分量表供人工审核及用户明确要求的专项评估使用，不是日常图片交付前必须自动执行的评分流程。待审图片可以交付，但不能标成图像内容、合规、质量或发布验收通过；没有实际审核的项写“未测”。生成前材料阅读、产品事实冲突处理、参考识别和策划确认要求仍必须执行。

## 发布硬门槛

实际审核发现以下任一项失败时，本案例不能标记为验收通过；默认待审状态不等于这些项目已通过：

- 使用了错误产品或混入其他产品事实；
- 对外名称和包装名称规则错误；
- 与当前产品已确认的标准表达、适用范围或禁用项冲突；
- 营养数据、份量、单位、配料或冲泡方法错误；
- 出现无法证明的医疗、疾病或健康功效；
- 虚构个人真实体验、认证、研究或来源；
- 产品严重畸变、镜像或包装无法识别；
- 将竞品品牌、产品外观或他人经历冒充目标产品/发布者，或超出允许复用范围照搬原文；
- 未读取参考却声称已看完，或编造缺失页面、数据与表现；
- 生图请求遗漏显式尺寸，或实际像素/比例不符合任务要求却标为通过；
- 用户提供过参考图文，但待生成页没有把原帖参考图放入实际 `image_paths`，或提示词未说明参考强度；
- 未分别明确叙事逻辑、逐页构图、图片风格和文案语气的参考程度，就把模糊的“参考一下”直接当成完整方案或开始生图；
- 忽略用户明确的参考范围，将局部参考擅自改成全篇迁移；
- 把旧包装名称和当前对外名称的已确认差异误当成必须阻塞的冲突。
- 未递归读取用户指定任务目录，遗漏会改变策划或生图的材料，却直接开始产出；
- 产品名、核心卖点/固定表达、用量或包装信息存在未解决冲突，却生成策划 HTML 或调用生图；
- 未先交付策划 HTML 并取得该版本的用户明确确认，就调用生图 MCP；
- 参考图没有逐张实际识别及机器可读语义清单，或语义 ID 与请求路径错配；
- 声称专项独立视觉评估已通过，却只有内容 Agent 自述或自造评分，没有真实独立评估记录；
- 专项评估中的严格参考页未达阈值却标为通过，或重试时自行降低参考、产品、文字、事实或素人感标准；
- 要求素人感时仍呈现明显棚拍、完美对称、统一精致道具、商业轮廓光或每页产品英雄位，却被标为验收通过。

## 100 分评分

| 维度 | 分值 | 评价重点 |
|---|---:|---|
| 任务理解与内容策略 | 15 | 人群、场景和四维参考合同清楚；拆解有依据，迁移方案符合范围 |
| 标题与正文 | 20 | 主体和真实经历边界一致；标题承诺可兑现、开头具体、信息推进、有依据的细节与自然产品衔接，不堆卖点 |
| 产品事实与名称 | 20 | 产品、口径、固定表达和关键词准确 |
| 视觉策划 | 20 | 逐页拆解与分镜对应；原帖图和产品图都进入映射，参考强度与角色清楚、产品可还原 |
| 平台适配与差异化 | 10 | 阅读节奏合理，避免照搬和过度同质 |
| 合规与风险处理 | 10 | 风险识别充分，保留必要人工审核 |
| 可执行与可追踪 | 5 | 输出能进入生产，含标签、测试假设和版本信息 |

实际执行该评分时，单个案例总分达到80分且全部硬门槛通过，才算该范围验收通过；不因默认交付而补造分数。

需要文案审稿时参考[自然文案方法](copywriting-method.md)。用户明确要求专项视觉评估时，按[专项评估合同](workflow-gates.md#6-可选专项独立视觉评估与有限重试)指出实际参考页与构图维度，不以“高级/素人感强”代替具体比较。尺寸预检、实际文件头像素检查、所请求的视觉评估和业务审核分别记录；未做写“未测/待人工审核”，脚本成功不代表视觉、事实或业务验收通过。日常人工审稿不必生成独立评分JSON。

## 策划交付检查

内容策划方案应先以轻量只读 HTML 交付，并能在对话中直接修改；末尾只保留会改变下一步的 0—3 个关键问题，不把标题、正文和参考程度拆成大量确认点。问题未回答时只暂停依赖部分，不能把初步假设写成用户已确认。产品关键事实冲突属于整体阻塞：必须在生成 HTML 前解决。

## 验收集接入

实际案例与验收范围由当前项目指定，位于 Skill 包外。不得自行减少已约定的案例或把新规则的行为测试代替业务验收。来源缺页、产品资料待定或图片未测应分别记录，不得推测为通过。

## 缺陷记录

每个失败点至少记录案例 ID、Skill 版本、产品资料来源/版本、参考意图、模型和 MCP 版本、缺陷位置、人工修改内容、缺陷类型、严重程度、是否阻止发布和修复版本。
