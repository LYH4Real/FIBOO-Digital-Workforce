# FIBOO 小红书内容策划

Windows 上执行本文的 Python 命令时，可使用 `${CODEBUDDY_PLUGIN_ROOT}/scripts/run-python.ps1` 自动发现 WorkBuddy 自带 Python 3.10+：`powershell.exe -NoProfile -ExecutionPolicy Bypass -File "${CODEBUDDY_PLUGIN_ROOT}/scripts/run-python.ps1" "<实际脚本绝对路径>" <原参数>`。脚本路径及参数必须替换为当前真实路径，不要求员工预装系统 Python。

将产品资料与本篇参考图文转化为可审阅的小红书方案。产品事实、缓存、业务图片都在用户工作目录维护，不写入 Skill，不自动发布或投放。

执行参考文档中的命令时，`scripts/...` 相对于本 SKILL.md 所在的安装目录，不是用户任务目录。先解析安装位置，实际调用使用带引号的脚本绝对路径；含空格的所有材料/输出路径也加引号。不要在任务文件夹重写一份同名脚本。

所有 `<task>`、`<product-work>`、`<skill>` 都是说明用路径约定，先替换成当前机器上实际可写的任务/产品材料目录和本 Skill 安装目录，再执行命令；不要把尖括号字样当成真实路径。

## FIBOO 市场依赖与入口

本插件的原生依赖声明包含 `fiboo-product-materials`、`dingtalk-cli`、`xiaohongshu-note-fetch`、`kimi-webbridge`、`wave-image`。首次用到对应能力时核对插件已启用以及员工自己的登录/配置状态；安装不等于授权已完成。独立做本地附件策划时不调用无关服务。

- **FIBOO 产品资料**：优先使用 `fiboo-product-materials` 实时获取公司钉钉记录、PDF 和主图，按[市场工作流接入](references/fiboo-marketplace-workflow.md)交接；用户指定的附件和说明仍保留并比较。不依赖旧的静态产品知识库或维护者电脑目录。
- **小红书参考链接**：使用 `xiaohongshu-note-fetch` 获取正文与有序原图；需要已登录浏览器时使用 `kimi-webbridge`，读取该插件当前操作说明。获取失败要保留原因，不能把网页链接当作已读参考。
- **生图**：使用 `wave-image` 当前暴露的 MCP 工具。宿主可能给工具名加插件前缀；以工具列表中的实际名称调用，以 `generate_image` / `edit_image` / `generate_batch_images` / `edit_batch_images` 语义匹配，不硬编码其他宿主的专用前缀。生产参数仍遵守本 Skill 的预检与确认要求。

## 先选入口，按需读文档

- **整理/更新产品资料**：用[产品预处理](references/product-preparation.md)。实际读取产品文档和图片，解决关键冲突后建立有来源、有版本的本地产品包；不策划、不生图。没有预建知识库也能做。
- **产品包已就绪，做一篇新内容**：用[单篇快速生产](references/fast-production.md)。校验源文件未变化，复用产品解读，只读本次 brief、新增参考及相关缺口；一次编译策划交付物。
- **没有产品包，直接策划**：用[产品资料接入](references/product-knowledge-contract.md)和[阶段文件合同](references/workflow-gates.md)完成冷启动。先询问会影响结果的缺口，不能为了进入快线把旧 AI 输出当成已确认资料。
- **只做参考拆解**：用[参考拆解与四维合同](references/reference-analysis.md)，无需产品包或策划批准。
- **执行已确认策划/重做失败页**：用[执行效率与请求编译](references/execution-efficiency.md)，重新核对批准与输入版本，再作图。修改文案、页序或提示词先产生新策划与 HTML，旧批准不能沿用。

不要一次读完 references 全目录。需要写文案时读[自然文案方法](references/copywriting-method.md)和[内容类型](references/content-types.md)；设计画面时读[参考驱动视觉方法](references/visual-prompt-method.md)；实际调用或处理生图失败时读[MCP 参数合同](references/image-mcp-contract.md)及[生图工作流](references/image-workflow.md)。这些方法不因快线而降低标准。

食品、营养品或保健食品任务在写标题、正文和图片文字前，读取[食品与平台表达规范](references/food-platform-rules.md)。同轮已读且渠道/产品未变时复用，不再启动审核 Agent 或每篇重搜整套法规；规则存在冲突、已过期或切换投放渠道时再核查。

## 每个入口都要遵守的生产约束

1. **先确认材料范围。** 枚举用户指定目录，识别本次输入、产品资料、历史输出。递归扫描明确的输入范围，排除已确认的历史/输出目录；不反复全盘读图，不靠文件名猜内容。说明已读、不可读、缺失三类结果。只向用户提出真正影响下一步的 0—3 个合并问题。
2. **关键产品事实有冲突就停。** 名称、卖点/固定表达、用量、包装信息冲突，必须在策划 HTML 前提问。不能自行选最新稿、杜撰“新旧名称分工”、换计量基准消除矛盾，或把 Agent 写的 confirmed 当批准。个人经历不可编造。缓存未变化只证明版本一致，不证明资料真实；新 brief 与缓存冲突仍先 HITL。
3. **参考必须实际看过。** 新图逐张用视觉能力识别，留机器可读语义清单；OCR/文件名不替代视觉。未变且有真实记录的语义可复用，图变则重看。逐页明确叙事、构图、风格、语气的参考程度；用户只说“参考”就给建议并用一个问题确认。严格构图替换不等于默认全篇复制。
4. **先策划，再批准，再作图。** 策划 JSON 为正文/逐页提示词的唯一创作源，由程序生成轻量只读 HTML；不建交互审稿台，不反复手写多套相同资料。交付 HTML 后停止；仅用户明确确认该版本后才留真实确认原话和文件哈希，调用生图。缺产品正面图、严格参考缺原图或关键意图不明确时，停止相关阶段并补问。
5. **原图必须进入真实请求。** 用户提供了参考图文，不论轻度或严格，每个待生成页均用编辑工具，实际传入对应/最接近的原帖图；所需产品图追加在后。缓存描述不替代图片。每页硬性指定 size，无其他要求建议 `1248x1664`；按内容需要安排产品露出，不把历史 brief 的最低植入页数当通用规则。
6. **默认交付人工审稿。** 生图后仅做文件存在/非空、实际格式、数量、尺寸与比例检查，保存真实请求、逐页参数和 MCP 原始返回；失败不裁切冒充达标。默认不启动独立 Agent/视觉模型、不逐页裁剪放大、不打视觉分、不自动视觉返工，也不运行 `visual_review_guard.py`。技术检查后交付已有图片并列明缺页/尺寸问题，标注“图片内容未审，待用户人工审稿”，不因没有独立视觉工具而扣住交付，不声称包装、文字、事实或合规已通过。
7. **内容约束前置。** 区分具体 SKU 的法定类别、发布主体、自然笔记/蒲公英/聚光渠道与证据；“保健品牌”不等于每款都是保健食品。把参考中无依据的功效、伪造亲历和隐含因果在策划时改掉，不能先生成再靠审图兜底。真实口感与使用便利可在依据范围内自然表达；“用了以后状态更好”并不自动免于功效审查。品牌内部确认不替代法定资质或广告批准。

## 验收、返工与时间

默认停在“生产交付完成、人工待审”，不要求用户先审完才能取得文件。用户给出修改意见后，仅处理指定页和问题；不要把“严格参考”或“素人感”自动解释为启用专项验图。用户明确要求专项审图时，才用[视觉评估文件合同](references/workflow-gates.md)和 `visual_review_guard.py`，整图优先，仅对明确疑点按需放大，不覆盖原图。专项阈值：严格参考构图≥85、风格≥80；产品/文字/事实准确均须100；要求素人感时手机随拍≥80、商业广告风险≤20。只有另获自动重试授权时才按失败页返工，通常最多2次、最高配置3次；不扩大付费请求范围。JSON 校验器不证明真实独立评估发生，禁止编造分数或通过结论。

交付时按[质量标准](references/quality-rubric.md)区分技术检查、图片内容审核和发布审核。人工待审不是技术失败，也不是可发布；默认以 partial 结束计时并说明图片已交付、视觉未测。平台额度、云端报错、空返回与下载失败分类处理，禁止无限重试。

按[快速生产计时](references/fast-production.md)记录冷启动/产品预处理/热启动、等用户、生图、按需审图和返工；600秒是待实测目标，不是已实现承诺。不要通过少做页面、漏记用户已要求的专项审图、剔除失败任务或隐去预处理耗时制造达标。
